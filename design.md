# Purpose
Synthetic local task management: list, detail, and summary form one user-value slice backed by the local HTTP API and SQLite. The Python standard-library server binds only to `127.0.0.1`; `/` serves the bundled screen, `GET /api/tasks` returns the ordered list, `GET /api/tasks/<id>` returns one task, and exact `GET /api/summary` returns live total, completed, and pending counts from the same database.

# Scenarios
Start with the two seed tasks in a new disposable database, filter them case-insensitively at `#list`, open task 1 at `#task/1`, and set its completion state through `PATCH /api/tasks/1`. Open `#summary` from either list or detail to see total, completed, and pending counts, then use its list link to continue the journey. Loading, no-match, and request-error states reflect API outcomes; a successful summary refresh clears a summary-loading error without concealing a failed completion update. Same-document navigation waits for an in-flight completion update before fetching the destination, and the server orders database reads after an accepted update through its commit. A slow bounded PATCH may continue receiving its body without blocking unrelated task or summary reads; once its valid body is complete, the update is serialized with those database reads. While `#summary` remains active it refreshes from the API, so even when a reload's first summary request arrives before an older page's outstanding PATCH, the displayed counts converge after that update commits. Returning to the list, revisiting detail or summary, using browser history, reloading, or restarting with the same database fetches and displays the persisted state; an existing table is never reseeded over user changes.

# Limits
Loopback demo with a caller-supplied disposable SQLite path only. Summary counts are calculated on each exact `/api/summary` request from current task rows; no summary cache or alternate summary route is provided. PATCH accepts exactly `{completed: boolean}`, reads its size-bounded body before entering the serialized database update, uses parameterized SQL, and rejects invalid input without changing the database. An incomplete request can occupy its own daemon request thread but cannot hold the database-read gate. Task IDs outside SQLite's positive signed-integer range are treated as missing. There is no legacy database migration, arbitrary file serving, external request, external resource, browser storage, public deployment, or production authentication/authorization.
